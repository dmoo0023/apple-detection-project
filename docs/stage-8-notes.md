## What was built

1. **`scripts/prepare_yolo_dataset.py`** — Ultralytics expects images and
   labels in parallel `images/<split>/` and `labels/<split>/` folders (it
   finds one from the other by swapping `/images/` for `/labels/` in the
   path). Our raw images live in OneDrive and converted labels in
   `data/derived/labels_det/` (flat), so this script copies the currently
   labelled train/val images+labels into that expected layout under
   `data/derived/yolo_dataset/` — small enough to copy rather than symlink
   (simpler and more reliable on Windows), and git-ignored since it's
   fully regenerable from raw data + existing label files.
2. **`scripts/train_yolo.py`** — fine-tunes a pretrained YOLO model
   (`yolov8n.pt` by default) with `workers=0` (the brief's own note:
   Ultralytics' data loader can hang/crash on Windows otherwise), then runs
   the trained model on val and evaluates it through the **same**
   `src/evaluate.py` used for the classical baseline — so the two are
   directly comparable on identical metrics, not each reporting its own
   favourite number.
3. **YOLO box → apple circle conversion:** a YOLO detection is a box
   `(x0, y0, x1, y1)`; this project's geometry/evaluation code works with
   circles `(cx, cy, radius)`. Converted as centre = box centre, radius =
   average of half-width and half-height — a reasonable approximation
   since most detected boxes are close to square (apples are round), not
   an exact statement that every box is a perfect square.

## Learning curve so far (3 points)

| Run | Train images | Precision | Recall | F1 | mAP@0.5 | Count MAE | Count bias |
|---|---|---|---|---|---|---|---|
| `model-v1-first-fit` | 10 | 0.676 | 0.827 | 0.744 | 0.756 | 7.00 | +6.40 |
| `model-v1-20train` | 20 | 0.736 | 0.806 | 0.770 | 0.786 | 4.20 | +2.70 |
| `model-v1-31train` | 31 | 0.704 | 0.837 | 0.765 | **0.814** | 6.00 | +5.40 |

Plot: `results/learning_curve.png` (also `results/learning_curve.csv`,
regenerated by `scripts/plot_learning_curve.py` from every stage-8 run in
`runs/experiments.csv`).

**F1/mAP: flat-to-rising, plausibly nearing a plateau.** mAP@0.5 kept
climbing (0.756 → 0.786 → 0.814); F1 basically flat since 20 images
(0.770 → 0.765, within noise). Detection performance may already be close
to what this task/model combination can do without a bigger change
(more diverse training rows, a larger model, or real hyperparameter
tuning — Stage 8's still-pending item 3).

**Count accuracy: NOT monotonic — went down, not up, from 20 to 31 train
images** (MAE 4.20 → 6.00, bias +2.70 → +5.40). Reported plainly rather
than smoothed over: this is a real result, not a plotting error, and it's
a useful one — it's a concrete illustration of exactly why Stage 8 item 4
calls for repeating the best configurations across several seeds before
trusting a single run's number. With one run per point, there's no way to
tell whether this dip is a genuine regression (e.g. the new row-3 training
images being harder in some way) or just run-to-run noise from a single
training seed. **This moves seed repeats higher up the priority list**
than "wait for the curve to level off" — right now there isn't enough
information to know whether the F1/mAP plateau above is real either.

## A training-curve spike — 3/3 runs now, getting WORSE, needs investigation

All three YOLO runs show a sharp transient spike in validation loss
partway through training, and the pattern across runs is itself a
finding:

| Run | Train images | Batch | Spike epoch | Peak val/cls_loss |
|---|---|---|---|---|
| `model-v1-first-fit` | 10 | 4 | ~30 | ~100 |
| `model-v1-20train` | 20 | 8 | ~17-20 | ~230 |
| `model-v1-31train` | 31 | 8 | ~10-12 | **~400** |

Precision/recall/mAP all dip toward zero at the same point each time,
before recovering and climbing steadily to the final values.

**Correcting an earlier guess (again):** the first note guessed small
batch size; that was weakened when the spike recurred with a bigger
batch. **This is no longer "noise, probably fine" — it is 3/3 runs,
getting both earlier and more severe as the training set grows, which is
the opposite of what you'd expect from pure small-dataset randomness
settling down.**

**A second lead, checked and RULED OUT with actual numbers** (not left as
a guess this time): the spike moving earlier as more images/batches are
added looked like it could be the LR warmup-to-main-schedule transition,
which Ultralytics computes as `max(3 x batches_per_epoch, 100)`
iterations (`args.yaml`: `warmup_epochs: 3.0` in all three runs). Computed
precisely from each run's actual `results.csv`:

| Run | Batches/epoch | Predicted warmup-end epoch | **Actual spike epoch** |
|---|---|---|---|
| `model-v1-first-fit` | 3 | 33.3 | 27 |
| `model-v1-20train` | 3 | 33.3 | **15** |
| `model-v1-31train` | 4 | 25.0 | **10** |

The predicted warmup-end epoch is roughly constant (~25-33) across all
three runs, since the `max(..., 100)` floor dominates at this dataset
size — but the actual spike keeps moving earlier (27 → 15 → 10). **Does
not match.** Warmup-schedule timing is ruled out as the explanation.
**Honest status: still unidentified**, now with one concrete hypothesis
eliminated rather than left unchecked. Next things worth trying if this
keeps happening: Ultralytics' mosaic-augmentation cutoff
(`close_mosaic` setting), or simply running the same config with a
different seed to see if the spike's *position* is seed-dependent at
all or genuinely tracks dataset size.

**Still not currently breaking results** — `best.pt` is selected by
tracking fitness across all epochs, and every run recovers and ends
higher than where it started — but a spike that's tripling in severity
run over run is not something to keep setting aside. This should be
properly diagnosed before relying on this training setup for Stage 8's
full experiment series, not left as a recurring footnote.

## Why YOLO's own printed metrics differ slightly from ours

During training, Ultralytics prints its own mAP50 (0.805) — close to, but
not identical to, this project's mAP@0.5 (0.756). Expected, not a bug: the
two use slightly different box representations (Ultralytics' native boxes
vs. the radius-from-average-half-width/height circles this project
converts to) and Ultralytics computes metrics on all 20 val images in one
pass where this project's number comes from the same evaluation code every
other method is scored with. When reporting a method's score anywhere in
this project, use **this project's own evaluate.py output**, not a
training framework's own printed number, so every method is held to the
exact same measuring stick (rule 7).

## What could go wrong later

- Retraining as more labels arrive (the planned next step) will add real
  points to a learning curve — watch specifically whether F1/mAP keep
  climbing, plateau, or (if train and val stay dominated by just 1-2 rows
  each) stay suspiciously flat in a way that suggests the model is mostly
  learning this orchard's specific rows rather than apples in general.
- `runs/yolo/<run_id>/weights/*.pt` are git-ignored (rule: model weights
  aren't committed) — only the config/metrics in `runs/experiments.csv`
  and `results/` are kept in git. If a specific run's weights need to be
  kept long-term, that's a question for the student (Git LFS / DVC / a
  separate weights store), not something to assume.

## Terms used

- **Fine-tuning:** continuing to train a model that's already been trained
  on a large, different dataset (here, YOLO's standard pretrained weights),
  rather than starting from random weights — lets a small, task-specific
  dataset still produce a useful model, since the pretrained weights
  already know general shapes/edges/colours.
- **Learning curve:** a plot of model performance against how much labelled
  training data was used — shows whether more labelling effort is still
  worth it, or whether performance has levelled off.
