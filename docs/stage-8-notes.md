## What was built

1. **`scripts/prepare_yolo_dataset.py`** — Ultralytics expects images and
   labels in parallel `images/<split>/` and `labels/<split>/` folders (it
   finds one from the other by swapping `/images/` for `/labels/` in the
   path). Our raw images live in OneDrive and converted labels in
   `data/derived/labels_det/` (flat), so this script copies the currently
   labelled train/val images+labels into that expected layout under
   `data/derived/yolo_dataset/` — small enough to copy rather than symlink
   (simpler and more reliable on Windows), and git-ignored since it's
   fully regenerable from raw data + existing label files.
2. **`scripts/train_yolo.py`** — fine-tunes a pretrained YOLO model
   (`yolov8n.pt` by default) with `workers=0` (the brief's own note:
   Ultralytics' data loader can hang/crash on Windows otherwise), then runs
   the trained model on val and evaluates it through the **same**
   `src/evaluate.py` used for the classical baseline — so the two are
   directly comparable on identical metrics, not each reporting its own
   favourite number.
3. **YOLO box → apple circle conversion:** a YOLO detection is a box
   `(x0, y0, x1, y1)`; this project's geometry/evaluation code works with
   circles `(cx, cy, radius)`. Converted as centre = box centre, radius =
   average of half-width and half-height — a reasonable approximation
   since most detected boxes are close to square (apples are round), not
   an exact statement that every box is a perfect square.

## Over-counting fix: tightened the NMS IoU threshold (applies to all runs below)

Investigating the over-counting (student asked whether a loss-function
"overlap penalty" would help) found that YOLO already has exactly that
mechanism built in: **NMS (non-max suppression)**, which discards a
predicted box if it overlaps a higher-confidence box by more than a
threshold. Ultralytics' default threshold is 0.7 (only suppress boxes
overlapping >70%) — quite loose, letting near-duplicate boxes on the same
apple both survive. Tightening it to **0.3** (no retraining, a pure
prediction-time setting) cut `model-v1-31train`'s count MAE from 6.00 to
2.60 with F1 *unchanged or slightly better*. Made the standing default in
`scripts/train_yolo.py` and `scripts/make_yolo_overlays.py`
(`--iou`, default 0.3), and **re-evaluated all three logged runs** with it
so every result below uses it consistently. The old (iou=0.7) results and
overlays are kept too, in `*_iou0.7`-suffixed files/folders, not deleted.

## A training-curve spike — 3/3 runs now, getting WORSE, needs investigation

All three YOLO runs show a sharp transient spike in validation loss
partway through training. Investigated properly this time (read
Ultralytics' own installed source in `.venv/Lib/site-packages/ultralytics/
engine/trainer.py`, not just guessed) rather than left as an open
question — three concrete, verified findings, one of them correcting the
previous version of this note:

**1. The "4-epoch-wide spike" in the plots is partly a display artifact.**
`results.csv` logs 100 rows per run, but the actual number of *distinct*
validation values is much lower (19 / 39 / 51 for the three runs) —
validation metrics (loss **and** precision/recall/mAP together) repeat as
bit-for-bit identical values across groups of 2-4 consecutive epochs, then
jump. Confirmed with the raw numbers, e.g. `model-v1-31train` epochs 10-11
both show `val/cls_loss=391.69700` exactly, `precision=0.02900` exactly.
A matplotlib line plot draws that as a wide dip; the real underlying
*distinct* measurement is narrower than the plot makes it look. Exactly
why validation logs repeat rather than refreshing every epoch wasn't
pinned down (would need more time in Ultralytics internals than this
warranted) — it does not change what matters practically below.

**2. Severity is NOT escalating run-over-run — only the raw loss NUMBER
is.** Corrects the previous version of this note, which read "~100 →
~230 → ~400" as "getting worse." Comparing the actual **minimum
precision/recall/mAP** reached in each run (the metrics that matter, not
an unbounded loss value) tells a different story:

| Run | Min precision | Min recall | Min mAP50 |
|---|---|---|---|
| `model-v1-first-fit` | 0.093 | 0.182 | 0.074 |
| `model-v1-20train` | 0.025 | 0.142 | 0.006 |
| `model-v1-31train` | 0.029 | 0.304 | 0.010 |

All three crash to a comparably bad worst point (precision under 0.1,
mAP under 0.08) — runs 2 and 3 are similar to each other, run 1 is
actually slightly milder, not part of a clean worsening trend. Cross-
entropy-style classification loss is unbounded and can produce wildly
different-looking numbers (100 vs 400) for comparably bad predictions,
just because a handful of predictions landed at slightly more extreme
confidence values — the loss MAGNITUDE trend I reported last time
overstated how much worse things were actually getting.

**3. Confirmed this is below Ultralytics' own defined "serious problem"
threshold.** The trainer source has a built-in NaN/Inf loss detector
(`_handle_nan_recovery`) that reloads the last checkpoint and retries if
loss or fitness becomes non-finite — i.e. the Ultralytics developers
explicitly anticipate this class of instability during fine-tuning.
Checked our saved training logs for its warning message
(`"NaN/Inf detected... recovering from last.pt"`): **never fired, in any
of the 3 runs.** Our spikes are large but finite — a milder instability
than the threshold Ultralytics itself treats as requiring recovery.

**Revised conclusion:** consistent with a known, expected phenomenon —
YOLO's classification head, pretrained on COCO's 80 classes, needs to
rapidly re-specialise to this project's single "apple" class early in
fine-tuning, and on a very small, non-i.i.d. dataset (10-31 images) that
re-specialisation can be transiently rough before settling, without
crossing into genuine training failure. Not something to keep
re-investigating at this scale; worth a quick recheck once the training
set is much larger (where per-epoch gradient estimates get less noisy)
rather than treated as an open bug.

## Why YOLO's own printed metrics differ slightly from ours

During training, Ultralytics prints its own mAP50 (0.805) — close to, but
not identical to, this project's mAP@0.5 (0.756). Expected, not a bug: the
two use slightly different box representations (Ultralytics' native boxes
vs. the radius-from-average-half-width/height circles this project
converts to) and Ultralytics computes metrics on all 20 val images in one
pass where this project's number comes from the same evaluation code every
other method is scored with. When reporting a method's score anywhere in
this project, use **this project's own evaluate.py output**, not a
training framework's own printed number, so every method is held to the
exact same measuring stick (rule 7).

## What could go wrong later

- Retraining as more labels arrive (the planned next step) will add real
  points to a learning curve — watch specifically whether F1/mAP keep
  climbing, plateau, or (if train and val stay dominated by just 1-2 rows
  each) stay suspiciously flat in a way that suggests the model is mostly
  learning this orchard's specific rows rather than apples in general.
- `runs/yolo/<run_id>/weights/*.pt` are git-ignored (rule: model weights
  aren't committed) — only the config/metrics in `runs/experiments.csv`
  and `results/` are kept in git. If a specific run's weights need to be
  kept long-term, that's a question for the student (Git LFS / DVC / a
  separate weights store), not something to assume.

## Terms used

- **Fine-tuning:** continuing to train a model that's already been trained
  on a large, different dataset (here, YOLO's standard pretrained weights),
  rather than starting from random weights — lets a small, task-specific
  dataset still produce a useful model, since the pretrained weights
  already know general shapes/edges/colours.
- **Learning curve:** a plot of model performance against how much labelled
  training data was used — shows whether more labelling effort is still
  worth it, or whether performance has levelled off.
